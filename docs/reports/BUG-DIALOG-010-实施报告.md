# BUG-DIALOG-010 实施与审查报告

## 1. 产品结论

采用右上角轻量通知浮层：最多同时显示 3 条，其余严格按产生顺序排队；玩家可逐条关闭，自动消失计时只从通知真正显示时开始。浮层完全脱离主叙事文档流，六条连续通知不会把事件标题、正文或选项推离原位置。

## 2. 已确认根因

- `GamePage.vue` 原 `notification-rail` 是 `.main-area` 的普通 flex 子项，通知数量越多，占用的纵向高度越大，直接压缩并下推 `SceneArea`。
- `ui.js` 原实现对每条通知立即 `push` 并立即启动计时器，没有同时显示上限和等待队列。
- 旧 DOM 把整条通知当点击目标，没有明确关闭按钮；读屏语义也无法区分消息与关闭操作。

## 3. 实现方案

- `ui.js` 新增常量 `NOTIFICATION_VISIBLE_LIMIT = 3` 与 `notificationQueue`。
- 前三条进入可见列表并开始计时；其余进入 FIFO 队列且不计时。关闭或自动消失一条后，立即提升队首并从此时开始其完整时长。
- `duration=0` 的错误或需确认消息永久保留至手动关闭；新增统一清理动作，避免遗留计时器。
- 通知轨改为 `position: fixed`，桌面固定右上角，390px 使用视口内满宽；轨本身不拦截页面操作，仅通知卡与按钮接收点击。
- 每条通知提供独立可访问关闭按钮；队列显示“另有 N 条通知排队中”。
- 未改通知业务内容、奖励结算、成就判定、签到数据或存档结构。

## 7. 审查结论与剩余风险

- 代码与玩家实际体验均完成：通知不再参与主事件布局，显示上限、排队、自动消失、手动关闭均有单测和真实浏览器证据。
- 极窄屏上三条通知会暂时覆盖部分角色状态，这是浮层设计的可预期代价；它不会改变或丢失叙事位置，且可立即手动关闭。
- 浏览器调试中出现的失败均来自验收脚本等待动画、TransitionGroup 离场节点和关闭按钮文本变化；最终已改为稳定布局后采样及只读取 `.toast-message`，完整链复跑通过。
