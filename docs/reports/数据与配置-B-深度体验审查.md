## 一、数据层现状盘点（玩家视角）

| 部分 | 规模 | 对"游玩舒适度"的直接含义 |
|---|---|---|
| JS 脚本启动瞬间 | 7 个 `<script>` 共 **≈817 KB 未压缩、全部 render-blocking**（game.js 300KB + expanded 258KB + data 135KB + 其余 124KB）+ game.html 内联 134KB | 弱网/移动端首屏白屏时间不可控 |
| 数据 JSON（13 个） | ≈666 KB，`loadData` 用 11 个 `Promise.all` 并行 fetch | 任一组数据失败都静默降级为"空" |
| 图片资产 | **225 张 ≈119 MB 未优化大图**（`scenes` 20 张、`spirits` 70 张、`beasts` 30 张、`locations` 26 张…），单图最大 1.28 MB | 每次事件加载一张 0.4~1.3 MB 场景图 |
| 基础事件库 | `game-data.js` 65 个 + `game-events-expanded.js` 275 个 = **340 个**；另有 `spirit-events.json` 168 条按武魂注入 | 内容量本身很足，不是风险点 |
| 图鉴/配置 | 武魂 70、魂兽 30、魂环 12、魂骨 31、NPC 33、地点 27、成就 72、结局 27、称号 41 | 全部有图，无真缺失 |
| 数值配置 | 技能树 4×5=36 点（Lv.90 可点满）、挑战塔 20 层、签到 7 天、锻造 8 配方、商店 12、任务 15 | 平衡性有 1 处明显矛盾（见 B-06） |

**结论：板块 B 的"内容量"和"配图覆盖"是健康的（这是好消息）；真正舒服度问题集中在"加载/渲染消耗"、
"按地点/阶段拆池后出现碎片化"、"数据键名多套体系导致的肉眼负担"、"随机奖励与替代做法的数值矛盾"四个方面。**

## 二、问题清单（按 P 分级）

### B-01　首屏与每次噪声：静态资源无缓存头、无压缩、无懒加载（P1·性能）

- **现象**：`server.js` 仅 `express.static`，未配置 `maxAge`（默认 `max-age=0`）；
  7 个脚本 `<script>`（无 `defer/async`）；assets 图片无 `sizes/srcset`，事件图用整个大文件原图。
- **数据印证**：脚本与 JSON 合计 **≈1.5 MB 未压缩**；`.jpg` 平均 **530 KB**，最大 1.28 MB；
  29 张图超过 1 MB；整个 assets 目录 119 MB 放在 public 下随项目一起发布。
- **玩家感受**：（新设备/弱网）至少等待第二次以上才能看到第一段剧情；网络波动时"图先出、字后出"或反之，
  事件正文与图片互相拉扯，体感卡。
- **建设性建议**：
  1. `express.static` 开启 `maxAge`（assets 目录用 `immutable`，其余按需）+ 开启 `gzip/brotli` 压缩中间件；
  2. 把 `game-events-expanded.js`（≈258KB）、`game-visual.js` 设 `defer`，`game-data.js` 留同步首屏；
  3. 图片压缩转 `webp/avif` + `sizes/width` 占位（见 B-02）。

### B-02　事件图：每次换事件都在换一张大图，且无宽高占位（P1·体验）
- **数据**：事件 340 个，按 `renderScene` 每次都重新构造 `<img class="scene-img">`（game.js:2583），
  场景图平均 **530KB/张**、最大 1.3MB；**高频复用**的图：`border_town 33 次`、`academy_classroom 32 次`、
  `temple 32 次`、`forest_outer 23 次`——但因为是每次 `<img>` 重建，首次出现仍要重新拉整图。
- **玩家感受**：点击选项 → 图片空白一阵 → 文字先出 → 图片加载后页面跳动（无 `aspect-ratio/width` 占位，
  `.scene-img` 只设 `max-height:340px`）。手机端还额外吃掉数据流量。
- **建设性建议**：给 `scene-img` 固定 `aspect-ratio` 或用尺寸占位；事件切换前对下一张图提前 `preload`/低分辨率占位；
  对**常驻于同一地点的系列事件**可复用已加载的场景 `<img>`（缓存 DOM），避免重复整张下载。

### B-03　loadData 静默降级：某个 JSON 失败 = 世界半空，没有任何提示（P1·信任）
- **现象**：`loadData()`（game.js:353-365）每个文件 `.catch(()=>({}))` 吞掉错误；失败时武魂/图鉴/地图/魂技
  数组为空却无任何 UI 提示，`init` 只对 `loadData`「整体」的返回做一次 `toast('数据加载失败…')`（且 A5 已指出"继续冒险"仍可点击）。
- **玩家感受**：瞬间看到武魂列表/图鉴全灰，或进入游戏后武魂/魂环/地点凭空"丢失"，玩家认为是自己档坏了。
- **建设性建议**：A 板块的「缺文件 + 重试」方案直接复用；在 `loadData` 每个 `.catch` 处累计失败文件名，
  若 `失败数>0` 则首页给出明确错误卡片（含重试按钮），不进入半空世界。

### B-04　事件"阶段×地点"有效池不均：依赖正则落点，部分走廊几乎空闲（P2）
- **数值**（实测 340 事件）：全球事件(全地图可用)只有 **20** 个，且分布是 academy 2 / adventure 1 / master 3 / **god 14**——
  god 独占 70%，低中段根本不共享。具体地点分布：
  史莱克学院 104（其中 academy 段 95 + global 2 = **97**，充沛）；天斗城 61、星斗外围 53、天空城 29、星斗深处 14、
  海神岛 10、落日森林 9、远古遗迹 9……冰封森林、龙之谷、七宝琉璃宗 各 1~3。
- **阶段错位**：**adventure（lv7-18）**在 `海神岛 / 武魂城 / 星斗深处` 的有效池仅 **2 / 2 / 3** 个事件——
  玩家刚出新手村四处跑时，可能在某个地点点几下就"今日无事件". 虽然 `availableEvents()` 为空时给
  "休整一日＋25 经验"兜底（不至于死机），但连续几次"休整"会让玩家怀疑是 bug。
- **根因**：事件 `location` 字符串经 `classifyEventLocation()` 正则落库无人工校验；`phase` 只绑到等级区间、
  与地点无关联，故个别阶段×地点组合下 `empty pool`。global 事件数量太低加剧了这一点。
- **建设性建议**：
  1. 给 adventure/master 各补 5~8 个"全地图可用"的通用事件（现在 global 里 adventure 只有 1、master 只有 3）；
  2. 当 `availableEvents()` 为空时，不再只用"休整"，而是给"附近还有事做的地方"（按权重推荐高密度地点）；

### B-05　"地点三套键 + 事件名称重复"给维护和玩家造成双重负担（P2）
- **现象**：
  - 地图层有 **3~4 套键**：`map-data.json`（英文 id：`shrek_academy`）／`map.html` LOCATIONS（中文 id）／
    `location-codex.json`（中文 id：`史莱克学院`）／事件字符串（`史莱克学院·教室`），多套并存靠手写映射连接（索引 F1 已标⚠）。
  - 事件**中文名重复**：实测 3 组 6 个同名事件——`商队护卫`（`caravan` 无等级 + `adv_sp_14` min18）、
    `时空乱流`（`god_big_12`、`god_more_03_rift` 同 min88）、`收徒`（`dy_sect_01` min5 与 `ma_more_04_mentor` min50）。
- **玩家感受**：明明同一标题，内容/地点不同；在"史莱克学院·教室"待上 7~8 步就可能再次点到同名事件，
  新鲜感断裂；遇到地点没有对应数据时还会出现"地图说了去但事件里找不到"的割裂感。
- **建议**：抽一层统一 `LOCATION_TABLE`（中文名 ↔ 地图 id ↔ codex id），事件直接引用 id 而不是正则文本；
  同名事件 6 个全改唯一名（或加阶段区分，如「收徒·幼年」「收徒·封号」）。
- **补充**：`validate-data.js` 目前只查「JSON 可解析 + 事件图片引用 + location 可归类」，
  **不查**事件名重复、不查 codex 图是否存在、不查数值分布——本次发现的 6 个同名事件都静静躺在数据里未被拦下。
  校验器升级方向见 B-07。

### B-06　奖励分布总体健康，但存在 2 处"反体验"数据
- **好的方面**：实测 340 事件中 51.2% 为 3 选项；奖励中位数随阶段平滑抬升（gold：academy 20 → adventure 30 →
  master 100 → god 300）；9 个魂环事件分布在 min 10/20/…/90 各自阶段、路径唯一；带战斗选项的事件 56 个，节奏清晰。
  高额单体奖励（attack+50/defense+50/exp+5000）集中在 90 级以上的 `god_daily_06`；`+20 属性` 级别的事件（`god_big_15` 等）
  都在 90~95，未发现低等级就白送大属性。
- **问题点**：
 1. **修炼 vs 商店数值倒挂**：训练「高强度修炼」200 金币→150 经验（0.75 exp/g），商店「经验丹」200 金币→500 经验
    （2.5 exp/g，**3.3 倍**）。老玩家很快会发现"修炼是亏的"，只剩商店买经验一个最优解——
    修的是配置数字的一致性，而不是砍掉商店。
 2. **负向随机少且段位不清**：`gold` 负值 19 处（adventure -50 / master -30 / **god -300**，academy 段没有负金），`damage` 选项 93 处
    中位仅 20，玩家几乎感觉不到"冒险选择有代价"；但由于兜底"休整恢复"，实际危害低。建议作为取舍：想保留点刺激 →
    把负值/伤害选项往"必定后果"改写并标红，否则删掉无谓的 -N。
- **建设性建议**：高强度修炼 exp 调回 ≈450/200g（与商店同量级）；高单体事件加显式前置（如"已完成第 8 环"）
  而非单看 minLv，在 god 段制造真正的选择题。

### B-07　内容规模达标，但"配图/别名/校验"依赖手写，维护进入死角（P2·维护与体验挂钩）
- **现状**：340 个事件平均正文 60 字（min 23 / max 172），节奏快、耐读；**图片全覆盖**——225 个资源文件被引用、
  事件 340 张配图逐条 resolve 全部存在，**0 真缺失**（B4 的 ❓ 已更新为 ✅）。
- **代价 1（视觉疲劳）**：事件配图高度集中在少数场景文件——`border_town 33`、`academy_classroom 32`、
  `temple 32`、`forest_outer 23`、`abyss_godrealm 23` 次；连续游玩几小时后同一张图反复出现。
  这本身复用合理，但"今日在学院"连续 10+ 次都跳同一张 `academy_classroom` 就更显单调。
- **代价 2（别名链脆弱）**：事件 `image` 用英文键，靠 `EVENT_ASSET_ALIASES`（game.js:255，30 条）运行时映射到中文文件；
  新增魂兽/场景若不同步别名，会出现"事件显示英文键、图片 404"，而**他人改名后容易漏同步**。
- **代价 3（校验盲区）**：见 B-05「补充」——`validate-data.js` 不查重名、不查 codex 图、不查图片分布。
- **建议**：
  - 事件名唯一性检查 + codex image 存在性 + 按阶段地点的最小事件带宽告警 + 大图阈值告警，全部并入 `validate-data.js`；
  - 把 `EVENT_ASSET_ALIASES` 内容并入统一 `LOCATION_TABLE` 的来源文件，干掉第二张清单；

## 三、给"玩家视角"的结论（除非验证，按 P 表）

1. **板块 B 没有阻断性 P0**：没有打不开、没有真缺图、没有事件爆权乱派；但也**没有任何 P0 之外的"伤筋动骨"**
   （真正的存档级事故仍在板块 C）。
2. **最值得当晚修的三件**（合并 A 板块已提的方案）：
   - B-01 / B-02 资源层：缩图 + 缓存头 + `defer` + 事件图宽高占位；
   - B-03：让 `loadData` 失败可辨识、可重试（复用 A4/A5 的「缺文件 + 重试」）；
   - B-04：补 3~5 个**全地图通用**默认事件（adventure / master 的 global 现在只有 1 / 3 个，是硬空档）。
3. **次一批（一两天）**：同名事件改名、训练/商店数值回调、统一 `LOCATION_TABLE` 并让事件引用 id。
4. **不急着做**：技能树 Lv.90 点满 36 点属作者有意设计，可保留；个别地点事件少是**特性**而非 bug，
   但给"只有 1~2 个事件"的地点加"在附近可能还有事做"的提示会更好。

## 四、给后续板块（C/D/E…）的校验钩子

- **数据守恒**：任何页面展示的 名称/图片/数值，都能追到**唯一一条配置记录**，且该记录有唯一不重复的 id。
- **图片守恒**：凡玩家可见的图，都必须存在、可解析、体积 ≤ 阈值（建议先压场景图，再对大图做发布告警）。
- **奖励守恒**：同样成本（金币/回合/次数）的两种做法，期望回报应在同一量级（B-02、B-07 已暴露例子）。
